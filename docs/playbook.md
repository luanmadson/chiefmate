# Playbook: improving Chiefmate

The guide for the crew, and for anyone, changing Chiefmate itself. Read it whole before you start.

Chiefmate improves itself: the crew works on a copy of this repository and every change ends in a pull request. When the owner merges it, each installation updates itself within minutes, once its crew is free. That is why the rules below matter: a careless change reaches running installations.

## How the code is organized

| Place | What it holds |
|---|---|
| `src/server.mjs` | The app's web server and API. It listens on this computer only. With `remote_access`, a second listener (also on 127.0.0.1) for Tailscale Serve alone: `remoteSettings` reads the setting, `remoteRefusal` checks the tailnet name, the Origin, the allowed `Tailscale-User-Login` and that the device's tailnet address in `X-Forwarded-For` is not this computer's own (`tailnetSource`), `fromServe` checks once per connection that Tailscale's service opened it (its PID from `netstat`, `tailscaled.exe` in session 0 by `tasklist`), and `fromAfar` turns what would open a window into its version from another device (a session in the app, the development environment in the background) or refuses what works only on the computer, which the app doesn't offer there (`ui/afar.js`; a unit test checks both agree). In a lockdown, the remote listener still serves the app's files and answers the API with 423 and the lockdown's reason. |
| `src/runs.mjs` | How a run goes: the working copy, the crew in sequence, the review, the checks and the pull request. No step publishes anything: `ALWAYS_DISALLOWED` refuses the commands that start with a publication, and `crewGuard` (also used by the manager's conversation in `src/manager.mjs`) runs the guard of `src/guard.mjs` before each command to refuse the rest, however they are written. Several runs (of different projects) go on at once: what the app shows of each is in `live`, by run id. |
| `src/queue.mjs`, `src/schedule.mjs` | One run per project at a time, runs of different projects side by side up to the session's runs at once (`maxParallel`: `max_parallel`, or 4 during a boost, from `sessionNow` in `src/spending.mjs`); missions on their days and times. With less room than projects waiting, `pickNext` gives it in turn (`byTurn`): the runs marked to go first (`goesFirst`: `resumeFirst`; a new mark joins there), then the project longest without running (`lastRan`), then the queue's order; within a project, the queue's order. `turnOrder` (`queueInTurn`) is that order for the app, `focus` and the manager. A run paused in the middle of its work keeps its project's working copy (`holdsCopy` and `copyHolder` in `src/runs.mjs`, `copyHolders` passed to `pickNext`; `execute` checks it again): no other run of the project prepares the copy until it resumes, nor shows as next in `focus`. A pausing run leaves `live` only once its work is put aside and its record saved (`pauseForUpdate` is always awaited). The queue rechecks waits for a configured usage limit against the current settings and usage (`limitWaitCleared` in `src/runs.mjs`, with `effectiveLimits` of `src/spending.mjs`: the session's pause in place of the 5-hour one, as `checkLimits` reads it). A mission missed while Chiefmate was off or on standby runs once at the next chance, at once, with `run.due` (when it was due; `isLate`, past `LATE_MINUTES`), which the app shows as "Late, runs now" (`lateTag` in `ui/app.js`). |
| `src/steer.mjs` | The owner's focus (the Focus panel at the top of Operations, `drawSteer` and `steerCard` in `ui/app.js`, `.steer` in `ui/style.css`; `/api/steer`, with `preview` for the work going on a change would hold; `cli.mjs focus`, `project-pause`, `project-resume`, refused inside a step): the modes `free`, `focus` (`only`) and `paused-all`, the projects paused alone (`paused`), kept as `steer` in `data/state.json` with its latest `changes`; `holdReason` says why a project may not start new work, obeyed by the queue (`tick` and `focus` in `src/queue.mjs`), the schedule (a mission of a held project waits and runs once after), the autopilot (`idleProjects`, `autopilotApprove`) and the board's approved items (`startNext` in `src/planning.mjs`); `changeSteer` (the owner's choice for the work going on: finish, or `pauseLive(id, 'focus')` in `src/runs.mjs`), `until` with the state before in `previous`, brought back by `readSteer` (`by: "time"`); `onSteerChange` nudges the queue and the approved items; the app's line (`steerLine`), the manager's (`steerManagerLine`) and the `focus` news. The live sessions, the agents in charge and the manager are never held. |
| `src/power.mjs` | The power modes (the mark at the top, `drawPower` and the power dialog in `ui/app.js`; `/api/power`; `cli.mjs power`): standby (`setStandby`: `held()` stops the queue, the schedule's missions and the autopilot; the runs going on pause through `pauseAll('standby')`; kept as `power` in `data/state.json`), stopping Chiefmate and shutting the computer down (`stopSystem`, `shutDown`: the runs and the live sessions' turns pause as for an update, the manager's answer is interrupted, a countdown for a shutdown, then the mode "off" saved, `closeAllBrowsers` in `src/browsers.mjs`, the crew's processes under the server stopped (`crewUnder` in `src/watch.mjs`), Windows' `shutdown /s /t 0` (`powerOffCommand`, never forced) and the end; `cancelStop` until it closes), what the confirmation lists (`powerPreview`) and the start after a stop (`startPower`). While it stops (`stopping()`), no update begins and the manager and the live sessions start no new answer or turn. The watchdog leaves a Chiefmate stopped this way off (`off` in `findProblems`). From the remote access, only standby. |
| `src/sessions.mjs` | The live sessions: the profiles (the settings' own, then an automatic one per project and tool, never saved), the first message from the prompt builder; in the app, the conversation turn by turn (`deliverSession`: Claude Code through `runClaude` with `--resume`, Codex through `codex exec --json` and `codex exec resume`, `codexItem` for its events), the queue, the interruption, the pause of the turns for an update (or a stop, `src/power.mjs`) and their carrying on after it (`pauseSessionTurns`, `resumeSessions`), the external tools released to the project or profile (`sessionMcp`), the permission requests (`ASK_FIRST`, `answerPermission`, and `explainCommand`, which says in plain words what each one does, where, whether it can be undone and its risk), the history (`data/sessions/<id>.jsonl`, `sessionHistory`) and the manager's lines (`sessionsLine`); in a window, the window (Windows Terminal or PowerShell, `openConsole`); and finding, measuring (`appSessionPids` for the turns in the app) and ending their processes. |
| `src/guard.mjs` | The guard of a live session in the app: `publishing` finds what a shell command would publish however it is written (`git -C dir push`, `bash -c "git push"`, `gh gist`, `gh release`, `gh workflow` and `gh secret` writes under their own rules (`GH_RULES`, `GH_READ`), `gh api` or a web request that changes something on GitHub, such as opening a pull request), but not what only reads (`git remote -v`, `gh pr view`), the text of a heredoc written into a file by a command that does nothing else (`withoutWrittenText`: read as bash reads it, on the whole command only, never inside `bash -c`; nothing but cat or tee writes and `INERT` programs in plain words around the texts (`PLAIN_AROUND`), otherwise kept whole) nor the text of a lone `chat say` or `defect report` written in plain words (`isMessage`, `PLAIN_WORDS`), and the file runs as Claude Code's PreToolUse hook (`guardHooks`, in `--settings`) to refuse what the owner has not allowed. Its refusals become permission requests like those of `ASK_FIRST`, whose rules only match a command's first words. The manager's one exception (`--grants`): `plainPush` says whether a push could be allowed (one branch, alone or after `cd <folder> &&`, with only its messages redirected at its end, never the main one nor forced, `HEAD` and `heads/<name>` read as the branch they name by `pushParts`; each form of the same push gives the same target, so one grant serves them all), `pushFacts` what it would send, and `takeGrant` lets the push the owner allowed go once, for the same repository, branch, folder and source, within `GRANT_MINUTES`; `cli.mjs push` goes through the same grant. The main branch only in a project with `main_push: "card"` (`mainPushTargets`: its clone, its repository folder or its GitHub repository, passed to the hook as `--main-dir` and `--main-repo`): `mainPushTarget` says whether a push of it may get the card (alone, no option, the branch by its own name; never forced), `pushFacts` adds the files it changes and the migrations among them, a grant given for the main branch serves only that push, with the source still at the commit its card showed (`grantFor`'s `main`, `pushFacts`' `tip`), and each grant serves only its asker (the manager, or the "Work now" session in `--session`). `logPush` writes each grant given and used in `push-log.jsonl`, next to the grants. A `gh repo create` the manager tries is refused with a pointer to `cli.mjs repo-create`, the only way it gets a new repository (src/decisions.mjs). For the emergency lockdown (`src/lockdown.mjs`), the hook refuses every command while it is on, and `riskyCommand` finds what its detection weighs: a real path into a protected folder (`protectedFolders`) and recursive deletions (grave ones refused); the hook notes them, and the publications it refuses to the crew and the manager, as signals (`--who`: step, manager or session). |
| `src/owner.mjs` | The owner's local key: made once in `data/security` (`ownerKey`; its file, `ownerKeyFile` in `src/lockdown.mjs`, is one of `protectedFolders`, denied to the file tools of the manager's conversation (`CHAT_DISALLOWED`), the live sessions on Claude Code and the rescuer, as `data/` is to the steps) and never put in an environment. On this computer, a command that is the owner's needs it in the `x-chiefmate-owner` header (`isOwner`); `ownerOnly` in `src/server.mjs` lists what a command without it may do: what the command line lets an agent do, never as the owner (a route missing there needs the key). The command line marks who asks: every change the manager makes on the planning board (triage, order, restore, a decided status added or set) carries `by: 'manager'`, and a step's line for its speech bubble names its run (`/api/say`, always kept as the agent's); a session or a step never decides on the board (smoke test: the instructions' commands run as the manager, a step and a session, without the key and without a signal for the lockdown). The command line sends it from the owner's terminal only (`ownerHeaders`: never with `CHIEFMATE_RUN`, `CHIEFMATE_MANAGER`, `CHIEFMATE_SESSION` or `CHIEFMATE_RESCUER`; a terminal check would not help, since an agent's command can open the console as its input); an agent's engage of the lockdown goes as a step's (`by: 'step'`), never refused. The app gets it once per browser: `scripts/open.vbs` (the shortcuts and the notifications) asks the server to open the app's window (`openAppWindow`, `/api/owner/window`, at most once every 15 seconds; nothing opens in the smoke test) with a pairing code good once for two minutes (`pairingCode`), which the app trades for the key (`redeemCode`, `/api/owner/pair`) and keeps in its own storage (`pairOwner` in `ui/app.js`); a page without the key asks for that window by itself. The remote access keeps its own checks. |
| `src/lockdown.mjs` | The emergency lockdown: its state in `data/security/lockdown.json` (`readLockdown`, `isLocked`), read by every process, and `refuseWhileLocked`, called where something leaves the computer or goes on (`mergeRun`, `discardRun` and `closeReplaced` in `src/merge.mjs`, `openPullRequest` and `deliverToClone` in `src/workspace.mjs`, `repoCreate`, `openSession`, `updateNow`, `cli.mjs push`); the queue, the manager's deliveries, the sessions' turns, the self-update's check, the autopilot, the claude.ai reading and the prompt builder's reload wait on `isLocked`. `engage` writes the state first, then runs the hooks the server's start gives (`setLockdownHooks` in `src/cli.mjs`: stopping the runs, the manager's answer, the sessions' turns and the crew's browsers; resuming after `release`; telling the owner and the manager); `release` is refused from the remote access and for anyone but the owner. The detection: `recordSignal` appends to `data/security/signals.jsonl` (the guard, the command line's refusals to a step, the server's refused requests), `weigh` reads them against `RULES` (warn, then lock) within `WINDOW_MINUTES`, and `checkSignals` acts, run by `startLockdownWatch` when the file changes. The signals carry who ran the command and where (`run`, `step`, `session`, `cwd`, `command`), whether it was `refused` and a deletion's `target` (and whether it `existed`); `recordCreated` notes the folders a command creates outside the agent's own (`createdPaths` in `src/guard.mjs`, `data/security/created.jsonl`), only for a command the guard lets run. The stopped runs are kept as `stopped.runIds`. The owner's note (`addNote`, from this computer or the phone; also with `release`) stays in the alarm's `notes` and reaches the manager as the owner's message (the `ownerNote` hook). Every alarm released is recorded whole (`incidentEntry`: evidence, notes, the watch's review) in `data/security/incidents.jsonl` (`readIncidents`), and in short in the history of `lockdown.json` (`historyEntry`: that file is read before every agent's command, so it stays small). An alarm the detection engaged goes to the emergency watch (the `review` hook, `src/sentinel.mjs`), which keeps its review with `saveReview` and may release it with `sentinelRelease`, the one exception to the owner's release. `/api/lockdown` (GET, for the phone's screen; engage, release, note) in `src/server.mjs`, the only route the remote access answers during a lockdown besides the app's own files (they hold no data, so the phone can open the screen); `lockdown` and `unlock` in `src/cli.mjs`; the red button, band, release dialog (with the note) and the phone's screen in `ui/app.js` (`drawLockdownButton`, `lockdownBand`, `lockdownSummaryHtml`, `watchReportHtml`, `drawLockdownScreen`). Tests never stop anything real: they give made-up hooks and a temporary folder. |
| `src/sentinel.mjs` | The emergency watch (the Sentinel, its own team in the org chart: `watchView`, `watchTeamHtml` in `ui/app.js`): it reviews each lockdown the detection engaged, never one a person engaged. The checks, in code (`runChecks`): refused or harmless, the protected places against the state before (`snapshot`, taken without blocking the server by `startSentinel` every 10 minutes while unlocked into `data/security/baseline.json`; `protectedChanges`), the target created by the same step (`createdBySame`), anything sent out in the step's log (`stepCommands`, `commandsInLog`, `sendsOut`; a command counts as refused only by Claude Code's own error result for the guard's hook, `REFUSAL`, which a command's output can't forge), the kind of alarm (`alarmType`: `ALLOWED_TYPES`, with `githubRead`), a second alarm within `REPEAT_HOURS`, the manager involved (its final review step included). Two analysts (`askAnalyst`: a fresh session in an empty temporary folder, Claude Code with no tool at effort max, or Codex in its read-only sandbox with the guard at xhigh; `analystTools`: both on Claude Code for a sensitive project or without Codex), each with its own prompt (`analystPrompt`, the data marked untrusted) and a checked answer (`parseVerdict`). `decide` releases only when every rule holds (a "false alarm" below `MIN_CONFIDENCE` is unsure); `reviewIncident` acts (the stopped runs resumed but the cause, through the `resumeRun` hook) and tells the owner and the manager the whole report (`reportText`); a person engaging the lockdown again meanwhile (`engagedAgain`, set by `engage`) leaves it to the owner, and `startSentinel` reviews again an alarm whose review a restart cut short. A new kind of alarm it may release goes in `ALLOWED_TYPES`, with its check in `alarmType` and its fix in `fixHint`. `security.sentinel: false` turns it off. |
| `src/escalation.mjs`, `src/smtp.mjs` | Calling the owner outside the app when the emergency lockdown waits for them (`wantsOwner`: the watch escalated it or is off, or an agent or the manager engaged it; never a false alarm the watch released nor a lockdown the owner engaged). `startEscalation` (started by `src/cli.mjs`) calls `escalate` once per alarm (Telegram's `sendMessage` to every linked chat with the buttons Release, Keep stopped and Details, carrying a single-use code, `CODE_MINUTES`; the e-mail through `sendMail` in `src/smtp.mjs` when Telegram fails or isn't set up; again, with a new code, while nothing reached the owner: `RETRY_MINUTES` doubling, `MAX_CALLS` in all), keeps it with `saveEscalation` in the alarm's state and record, reads the bot by long polling (`pollOnce`, only while an alarm or a link is pending; no webhook, no open port) and takes the buttons off when the alarm is over (`tidy`). `handleUpdate` answers only a private chat linked with `/start <code>` (`startLinking`, `linkChat`), and silently ignores anyone else; Release asks for the PIN (`pinMatches` against the salted scrypt hash of `hashPin`; the PIN's message is deleted), `MAX_TRIES` wrong ones block it until `setPin` runs again; then `release` in `src/lockdown.mjs` with `from: 'telegram'`. The secrets (`readSecrets`: the token, the chats, the PIN's hash, the SMTP login) are in `data/secrets/escalation.json`, a protected folder (`secretsFolder`, one of `protectedFolders`), denied like the owner's key to the file tools of the manager's conversation (`CHAT_DISALLOWED`), the live sessions on Claude Code and the rescuer; the rest in `data/security/escalation.json`. The setup (`changeEscalation`: token, link, pin, email, test, remove) is behind `/api/escalation` (refused from the remote access), `cli.mjs escalation` (refused inside a step, the manager or the rescuer) and the Crew page's panel (`drawEscalation`, `fillEscalationDialog`, `#escalation-dialog` in `ui/app.js`); `escalationView` never holds a secret. The tests fake Telegram's API (`fetch`) and the e-mail (`mail`, or an SMTP server on 127.0.0.1). |

## Rules

1. **English everywhere**: code, comments, documentation and commit messages.
2. **Every text the user sees is translated.** On the server it goes through `t()` (`src/i18n.mjs`); in the app, through `t()` (`ui/i18n.js`) or a `data-t` attribute in `ui/index.html`. Write `t()` with a plain quoted string, and add each new text to `ui/locales/pt-BR.json` with a Brazilian Portuguese translation. `npm run check` fails when one is missing.
3. **No dependencies.** Node.js built-ins and plain browser APIs only. No build step. The one exception is optional: `playwright-core`, loaded on demand for the prompt builder's copy, with a clear message when it is missing. Nothing else may need it.
4. **Keep the settings compatible.** Installations update themselves, and their settings are not in this repository. A new setting needs a default in the code. Never rename or remove a setting without migrating it automatically.
5. **Security is not negotiable.** Don't weaken any of these:
   - the server listens on 127.0.0.1 only, the remote access's listener too;
   - the Host, Origin and `x-chiefmate` checks on every command, and on the remote access the tailnet name, the Origin, the allowed Tailscale login, another device's tailnet address and a connection opened by Tailscale's service on every request;
   - the owner's local key (`src/owner.mjs`): required on this computer for every command that is the owner's (`ownerOnly` in `src/server.mjs`), never in an agent's environment or command, and its file a protected place;
   - the safety headers on every answer (`SAFE_HEADERS` in `src/server.mjs`);
   - the file viewer: read only, its roots and protected names and places, the real path checked (`checkPath` in `src/files.mjs`), and its answers' headers (`rawHeaders`: no cache, no use by other sites, nothing run in the app's context);
   - the tools agents may never use (`ALWAYS_DISALLOWED` in `src/runs.mjs`, and the conversation's list in `src/manager.mjs`);
   - a step on Codex or Grok (`src/tools.mjs`): Codex's sandbox (`workspace-write`, never `danger-full-access`), its guard hook and `--ignore-user-config`; Grok's deny rules (`GROK_DENY`) and the owner's Claude Code and Cursor configuration kept out; the manager and the final review always on Claude Code;
   - the removal of the Claude session's variables in `src/claude.mjs`, and the flags that keep the user's own Claude Code configuration out of every step and every live Claude Code session (`--setting-sources project,local`, `claudeMdExcludes`, `--strict-mcp-config`; `sessionArgs` in `src/sessions.mjs` for a window, `claudeArgs` through `runClaude` for a session in the app);
   - what each step may see (`src/access.mjs`): only its project, its own documentation folder and the libraries it lists;
   - the watchdog's rescuer: only its closed list of actions (`src/watch.mjs`), no tool that changes files, and the `rescue` actions refused inside a step or the manager's answer;
   - the rule that only Chiefmate pushes branches and opens pull requests, and merges them only with the owner's authorization (`src/merge.mjs`; `cli.mjs merge` refuses to run inside a step);
   - the emergency lockdown (`src/lockdown.mjs`): what it stops and refuses, and its release, only by the owner on this computer (never through the remote access, a step, the manager or a command with no terminal), by the owner on their linked Telegram chat with their PIN (`src/escalation.mjs`: a private chat linked with its code, the PIN only as a salted hash, a single-use code per alarm that expires, the block after wrong PINs, the secrets in a protected folder and never in the app's state), or by the emergency watch (`src/sentinel.mjs`) under every rule of its `decide`, never reachable from the app, the command line or the remote access. A new way for something to leave the computer calls `refuseWhileLocked`;
   - the emergency watch's analysts: they only read what they are given (no tool on Claude Code, Codex's read-only sandbox with the guard), and the incident's data reaches them marked untrusted.

   Any change in these places must be explained in the pull request, under a "Security" heading.
6. **The look**: dark and formal, with thin lines, square corners and brass as the only accent color. No rounded, generic web look. The crew's faces are line art.
7. **Windows scripts** (`.ps1`, `.vbs`) are ASCII-only, with CRLF line endings. A launcher starts Chiefmate with `node src/cli.mjs server --log` and never redirects its output (`>> dataserver.log`): cmd keeps a redirected file locked while Chiefmate runs, and the self-update could not restart it.
8. **One improvement at a time**, small and complete. Update the README and this playbook when your change makes them outdated.

## Where the work comes from

2. If there are none: what you can see is weak. A bug, an unclear text, a confusing screen, a missing piece of documentation.

## How to test

- `npm run check`: the syntax of every script, and the translations.
- `npm test`: the unit tests (`scripts/unit.mjs`, `node:test`), with made-up files in a temporary folder.
- `npm run smoke`: starts a temporary Chiefmate on a spare port, with records of its own in a temporary folder, and checks that the app and the API answer. Never let it send a real message to the manager: that starts Claude Code. Never let it open a window, a browser or a program on the owner's computer either: test what opens things with `dryRun` (or `--dry-run`) and made-up settings.
- For a change in the app's look, describe in your report what changed and where, so it can be checked without reading code.
